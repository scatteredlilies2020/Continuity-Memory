# Continuity Memory for SillyTavern

Continuity Memory automatically builds and updates memory for long SillyTavern chats. It creates rolling summaries and saves important story details in the background, then recalls relevant memories for each reply. It works without Lorebooks or World Info and does not modify them.

## What it does

- **Keeps recent chat as-is.** New and unprocessed messages remain available in their original form.
- **Builds rolling summaries.** A detailed **Digest** covers each completed group of messages. Older history is combined into a **Recursive Chronicle**, which gives the response model a compact timeline of the story.
- **Saves important details separately.** It records facts, events, relationships, character and world states, and supporting observations, with links back to their source messages.
- **Recalls relevant memories.** When a reply is being prepared, it selects older details related to the current conversation instead of adding everything it has stored. Local matching is built in; AI-assisted search and semantic embeddings are optional.
- **Handles changes.** You can review and correct memory. If chat messages are edited, deleted, swiped, or branched, Continuity checks and repairs affected memory rather than treating it as settled history.
- **Keeps chats separate.** Each chat has its own memory, and Continuity does not change saved chat messages.

Memory processing runs in the background. If part of a chat has not been processed yet, those messages remain available as raw chat. Summaries and retrieval help with continuity, but they are not a perfect replacement for the original conversation.

Background building still starts at eight stable pending messages. With the default eight-message Digest batch, replies wait for extraction only at 24 or more stable pending messages. Each saved chunk rechecks that threshold: once fewer than 24 remain, the reply proceeds while any remaining extraction, Chronicle work, and queued jobs continue in the background. Embedding retrieval separately requires at least 90% index coverage.

Memory records history, not required behavior. Earlier refusals, agreements and knowledge apply at their recorded time; later play can change them. Recall shows knowledge with its source range and removes exact duplicate observations caused by changed character indices, while keeping the original stored history.

Author notes remain author-level context. Both Digest extraction and Chronicle parents use source-grounded semantic review when vocabulary overlap flags uncertain attribution. Confirmed violations or invalid reviews receive bounded corrective retries; failed sections remain pending. No recovery path copies raw source messages, statboxes, or author notes into generated Chronicle prose. Original chat sources remain untouched.

## Installation

1. In SillyTavern, open **Extensions** and choose **Install Extension**.
2. Enter this repository URL:

   ```text
   https://github.com/scatteredlilies2020/Continuity-Memory.git
   ```

The browser extension works on its own; the server plugin is optional. To keep memory jobs running after the browser tab closes, place the **whole repository** at `SillyTavern/plugins/continuity-memory`, enable `enableServerPlugins: true` in SillyTavern's configuration, and restart SillyTavern. Keep the `plugin/` and `extension/` directories together. SillyTavern must remain running for background jobs.

For Docker, mount the whole repository at `/home/node/app/plugins/continuity-memory`.

## Useful to know

- **Model usage and cost.** Extraction and Chronicle summarization make additional model requests, which may incur API costs. Extraction uses your active SillyTavern model by default; you can choose separate models for extraction, summarization, and AI-assisted retrieval. Local retrieval itself makes no AI requests.
- **AI search output handling.** AI-assisted retrieval accepts JSON wrapped in prose, code fences, or reasoning tags. Only unusable search-term output gets one rerun with brief format guidance, within the same time limit. If that also fails, the reply stops with a clear error; local retrieval is never substituted. No broader AI correction passes are added. Authentication errors, retrieval timeouts, and required memory/embedding catch-up retain their existing safeguards.
- **When memory updates.** Automatic processing is on by default, with 8 messages per Digest. Incomplete groups remain raw until the group is complete, so memory does not update after every message.
- **Compact memory output.** The automatic extraction target scales with the excerpt and covers the whole JSON response, including Digest and Chronicle text. A separate completion allowance leaves room for JSON and model reasoning; the target is guidance, and complete accepted summaries are kept intact.
- **Capacity-first Chronicle hierarchy.** Each layer fills to its configured node capacity (default 24). Only on overflow are the oldest same-layer nodes (default group of 10) summarized into one parent; recent C0 entries remain alongside older C1 entries. C1, C2, and every higher layer follow the same rule. The Story token target is only a parent-compression planning estimate, never a reason to collapse partially filled layers. Parents must shrink the complete rendered prose, including detail fields; bounded correction failures keep the original sources intact. All children remain stored, while recall injects only the active frontier.
- **Status and problems in settings.** Continuity’s extension settings show processing, retries, pending messages, and failures. Select Recent problems for the current status and problem history for this chat. Problems remain in a bounded history when a retry clears the current error, and failed server jobs are restored into that history after a reload. Background failures also show a popup when Popup messages is enabled. The status view lists browser and server versions and flags a server restart when they differ.
- **Storage reconnection.** A storage timeout shows “Reconnecting storage” and retries every 10 seconds while the tab is visible. A successful refresh clears the connection warning and resumes automatic maintenance without requiring Build. Connection history remains available, and genuine extraction errors stay visible independently.
- **Interrupted connections.** Server memory jobs retry automatically and keep completed sections. Repeatedly interrupted batches retry as smaller sections, with visible reconnection status. Stop still cancels the unfinished work and leaves it pending.
- **Generation streams and forks.** Server memory jobs accept both standard SillyTavern completion streams and AI SDK typed streams used by forks. Streamed reasoning counts as connection progress but is never saved as memory output. Restart SillyTavern after updating server-plugin code.
- **Context reduction is not deletion.** Older processed messages can be left out of requests to the response model to make room for summaries and recalled details. They remain in your saved chat and on screen.
- **Review before saving.** You can require approval of each Digest extraction and Chronicle promotion before it is saved. This is off by default; enabling it pauses processing for you to save, regenerate, or discard the result.
- **Recheck without starting over.** In Processing, the main controls are **Build → Recheck continuity → Rebuild Chronicles → Stop**; rollback and Digest undo are on a separate recovery row, and destructive reset stays behind its own disclosure. Recheck audits existing memory fields, Digest, supporting observations, and Chronicle parents against available original RP sources using the Correct memory model (falling back to extraction). It shows source-linked before/after patches; nothing is saved until **Apply repairs**, and a no-change review writes nothing. Correct records, source ranges and chat messages are retained. Only affected Chronicle parents are rebuilt after a repair. Unavailable or cross-chat sources, unresolved RP contradictions, missing records, duplicates and identity changes are flagged for manual review rather than guessed or automatically deleted; this is not a new extraction of pending chat. Changed/deleted source ranges must first be repaired with Build / Repair rollback. Checks are batched without sampling records, clipping source text, or imposing a total token cap; requests can expand their source context. Large individual source spans may still require a large context window. Progress shows approximate character-based input tokens, not actual billing or output/reasoning usage. Completed review batches resume in the same tab while sources, memory revision and model configuration match. Stop prevents unfinished reviews from being applied. A guarded **Undo last recheck** restores the pre-apply memory only if no newer memory or RP changes would be overwritten. Review checkpoints and this undo snapshot are session-only and are lost on reload or tab close.
- **Processing privacy.** Storing memory on your SillyTavern server does not mean model processing stays local. Chat excerpts used for extraction and memory used for summarization are sent to the model provider you configure.
- **Where memory is stored.** Continuity saves its own JSON files on the SillyTavern server, not just in browser storage or in a Lorebook. Within your SillyTavern user data directory (normally `data/default-user`), it uses `user/files` without the server plugin, or `continuity-memory/worlds` with it.
- **Lightweight shard upkeep (server plugin).** Old content-addressed shard versions no longer accumulate forever. Connecting CM or saving memory schedules one background sweep of all that user’s worlds, at most hourly: manifests and file metadata only, no AI calls or full-world loads. A world scans at most 1,024 obsolete files and deletes at most 256 per pass; a persistent cursor handles larger existing collections over subsequent visits. Current manifests and every local Syncthing-conflict manifest protect their referenced shards. Unknown files are left alone; invalid, incomplete, unsupported, or linked storage fails closed. By default, a shard must be observed unreferenced for a full **1 day** before removal (not merely have an old modification date). Reuse or changes reset its grace period. Change the server-side policy under **This chat’s memory → Storage upkeep**; saved policies are preserved, and `0` retains versions indefinitely. Increase the grace period for devices offline longer than a day: an old manifest arriving after cleanup can still require removed files. The same policy also removes expired CM backup copies under the default user `.stversions/continuity-memory` archive (including old vector backups) and CM’s `worlds/recovery-backups` folder. Backup age comes from the filename’s archive timestamp, since Syncthing preserves the original modification time. Each sweep scans up to 1,024 backup copies and deletes at most 256, with a persistent cursor for larger collections. Other applications’ backups and custom Syncthing versioning paths are left alone. This cleans obsolete physical versions and expired backup copies, not active Digest/Chronicle sources, archived structured records, raw chats, or saved embeddings. Active memory can still grow with history. Without the server plugin, this shard collector does not run. Restart SillyTavern after updating the plugin to enable it.
- **Memory also travels with the chat.** **Keep portable memory in chat files** is on by default. It saves a matching memory snapshot in the chat file's metadata and includes it in SillyTavern JSONL chat exports, without rewriting chat messages. Turning it off excludes the portable copy from saved chats and exports; the separate memory files remain. Exported chats can therefore contain remembered details as well as messages, so treat them as private.
- **Transferring memory.** Use JSONL chat exports to move a chat with its embedded memory, or **Export memory** / **Import memory** to transfer memory separately for the same conversation history. To carry memory into a different chat, use **Continue in new chat**, then **Start continuation arc** in the destination. Embedding vectors are stored separately and are not included in portable memory or exports.
- **Recovery and exports.** Automatic stored-memory recovery checks only candidates for the same named conversation or its saved memory ID, then verifies message fingerprints. A fresh chat does not search unrelated memories sharing the card's greeting. If memory is unavailable or cannot be verified during JSONL export, the chat messages still download, with a warning that Continuity memory was omitted. The original saved chat and memory stay intact.
- **Embedding proxy URLs and forks.** With the CM server plugin, custom/OpenAI-compatible embedding base URLs preserve reverse-proxy path prefixes and accept an optional trailing `/v1`: both `https://proxy.example/prefix` and `https://proxy.example/prefix/v1` use `/prefix/v1/embeddings`. CM keeps SillyTavern's saved VLLM key and host-specific request headers. Without the plugin, embeddings use SillyTavern's native vector adapter; older versions or forks may discard the path prefix. Use a base URL, not the full `/embeddings` endpoint.
- **Remembered connections.** CM keeps the last URL and model separately for Custom/proxy and OpenRouter, independently for extraction, retrieval, correction, summarization, and embeddings. Text changes are saved as you type. Passwords/keys are saved through SillyTavern's secrets service when you leave the field or switch provider; a blank field keeps the existing key. CM settings store only secret IDs, never passwords. Failed saves keep the draft in memory for retry; they do not survive a page reload. Embedding credentials still use SillyTavern's shared OpenRouter/VLLM key slots, so changing those keys elsewhere in ST affects native embedding requests too.
